# Golden vectors for `analyze()` and the normalization functions

These files are the executable form of `docs/spec/01` and `docs/spec/02`. The Python engine
(`backend/recruit_radar/engine/`) and the TypeScript engine (`src/engine/`) must both reproduce every
file **exactly**. They are implementation-independent: they were generated by a stdlib-only reference
oracle (`contracts/tools/oracle.py`) written from the spec alone, and the arithmetic was re-derived by
hand (`HAND_CHECKS.md`). Implementers must treat everything in this directory as read-only.

```
contracts/vectors/
  README.md                          this file
  HAND_CHECKS.md                     step-by-step hand derivations and whether the oracle agreed
  normalization.json                 173 cases for six functions
  analysis-NN-<name>.json            44 vectors, ONE vector per file
contracts/tools/
  oracle.py                          reference implementation + `--self-check`
  generate_vectors.py                the only writer of the files above
docs/spec/ambiguities/vectors.md     every place the spec admits two readings, and what the oracle chose
```

All files are **pure ASCII**: every non-ASCII code point is a `\uXXXX` JSON escape (astral code points as
surrogate pairs). Decode with a normal JSON parser and **do not normalize, trim or case-fold anything
yourself** - several vectors exist to catch exactly that. Line endings do not matter.

## `normalization.json`

```jsonc
{
  "format_version": 1,
  "kind": "normalization",
  "description": "...",
  "cases": [
    {
      "id": "norm_text-004",
      "fn": "norm_text",
      "input": "...",
      "expected": "acme 123",
      "note": "...",
    },
  ],
}
```

| `fn`                   | `input`                                                  | `expected`   | spec         |
| ---------------------- | -------------------------------------------------------- | ------------ | ------------ |
| `norm_text`            | string                                                   | string       | 01 section 2 |
| `company_key`          | string (company name)                                    | string       | 01 section 2 |
| `title_key`            | string (raw title)                                       | string       | 01 section 2 |
| `location_key`         | string **or `null`** (`null` behaves as `""`)            | string       | 01 section 2 |
| `token_sequence_match` | `{ "title": <title_key>, "phrase": <raw phrase> }`       | boolean      | 01 section 2 |
| `sha12`                | string (hashed as its UTF-8 bytes, **no normalization**) | 12 hex chars | 01 section 2 |

`token_sequence_match.title` is always an already-normalized `title_key` (the function's first
parameter); `phrase` is raw and is normalized by the function. `id` and `note` are for humans.

## `analysis-NN-<name>.json`

```jsonc
{ "name": "change-span-14-vs-13", "description": "why this vector exists",
  "input":    { "as_of": "...", "profile": {...}, "decisions": [...], "snapshots": [...] },  // 02 section 1
  "expected": { "as_of": "...", "companies": [...], "roles": [...], "events": [...],
                "merge_candidates": [...], "stats": {...} } }                                  // 02 section 5
```

- `input` follows `docs/spec/02` section 1 exactly. Every posting carries **all ten** RawPosting
  fields of `01` section 1 (optional ones as explicit `null`); `source_kind`/`source_ref` inside a
  posting always equal those of its snapshot; all strings are already trimmed; `""` is never used for
  `null`; every ATS posting has a non-null `source_posting_id` (only `csv`/`manual` may be `null`).
  Snapshots are listed in arbitrary order - sorting is the engine's job.
- `expected` is the complete `Analysis`. It is produced by the oracle, and the oracle's output for the
  committed `input` is asserted equal to it by `--self-check`.
- All numbers are integers. `null` is always present as a key (no omitted keys).

### How an implementation must consume them

Compare the **whole** `Analysis` with deep equality. Array order is significant (`companies`, `roles`,
`events`, `merge_candidates`, `aliases`, `observations`, `components`, `fields`); object key order is
not. Do not compare subsets and do not "normalize" before comparing.

```python
for path in sorted(glob("contracts/vectors/analysis-*.json")):
    v = json.load(open(path, encoding="utf-8"))
    assert analyze(v["input"]) == v["expected"], v["name"]          # dict/list equality
for c in json.load(open("contracts/vectors/normalization.json", encoding="utf-8"))["cases"]:
    assert call(c["fn"], c["input"]) == c["expected"], c["id"]
```

```ts
for (const f of readdirSync(dir).filter((f) => /^analysis-.*\.json$/.test(f))) {
  const v = JSON.parse(readFileSync(join(dir, f), 'utf8'));
  expect(analyze(v.input), v.name).toStrictEqual(v.expected); // whole object, order-sensitive arrays
}
```

A loader that globs `contracts/vectors/*.json` should dispatch on the file name: `normalization.json`
is the only file with a top-level `cases` array; every `analysis-*.json` has `input`/`expected`.

### If a vector fails

Do **not** edit the vector and do not special-case it. Either your engine has a bug, or the spec is
ambiguous. Check `docs/spec/ambiguities/vectors.md` first: it lists every sentence of the spec that
admits more than one reading, which reading the oracle took, and which vectors (if any) depend on it.
If your failure is not covered there, record it in `docs/spec/ambiguities/<your-role>.md` and report it.

## What these vectors are designed to catch

Places where two independent implementations of this spec most likely diverge:

- **Sorting is by code point, not UTF-16 code unit and not by locale.** `location_key` token order,
  `aliases`, alias/name tie-breaks, `a_key < b_key`, rank ties, `snapshot_id` order. Astral letters
  (CJK ext. B) vs. BMP characters above U+D800 (U+FE0F) order differently in UTF-16 (JS default `sort()`).
  An accented `e` (U+E9) sorts after `z`.
- **Lengths are in code points**: `near_typo` needs >= 6 _code points_; Levenshtein works on code points.
- **Normalization order**: bracket removal happens _before_ NFKC, so fullwidth brackets survive it;
  `title_key` removal deletes (no space inserted); `U+FE0F`/`U+02BC` are letters/marks (kept), emoji are not.
- **Boundaries** (the freshness formula is continuous at d=7 -> 1000 and d=60 -> 0, so the informative
  freshness points are d=8, d=59 and the clamp beyond 60): 30-day window is `as_of-30d < at <= as_of` (strict on the left); `age >= 45`; span `>= 14`
  vs `13d 23:59:59`; freshness `d <= 7` / `d >= 60` with seconds below the day boundary; token overlap
  exactly 75%; a snapshot observed exactly at `as_of` is processed, one second later is ignored.
- **Replay**: baseline is per source, not global; `additive` never removes; duplicate keys inside a
  snapshot (last wins, events in order of _last_ occurrence); `reappeared` is not `changed`; a rename
  is `changed` with sorted `fields`; removal order; `snapshot_id` string order (`"s10" < "s2"`).
- **Identity**: user merges apply to history and are transitive with the smallest key canonical;
  candidates compare _canonical_ keys only; `not_same` hides only its own pair; headcounts within one
  source never merge; null-id rows are keyed by (company_key, title_key, location_key); empty keys.
- **Scoring**: nulls are _missing information_, never zero (coverage), but a computed 0 is a real 0
  (`volume` with an empty scope, `urgency` with nothing aged); `rhu` rounding; corroboration cap and
  counting only _active_ observations; unscored companies sort last.

## Regenerating and verifying

```
.venv/Scripts/python.exe contracts/tools/generate_vectors.py     # rewrite every file
.venv/Scripts/python.exe contracts/tools/oracle.py --self-check  # verify; non-zero exit on any problem
```

`--self-check` re-computes every `expected` from its `input` and compares it with the file; checks that
all ids derive from their keys and every reference resolves; validates that every `input` conforms to
`01`/`02`; re-runs every vector under each alternative reading of an ambiguous spec sentence and
fails if any committed vector's `expected` changes (so no vector silently depends on an ambiguity);
compares the files with a fresh build; and asserts the hand-derived values of `HAND_CHECKS.md`.
